Twin-in-the-Loop rApps on a Virtual RIC

Capacity · slice · energy · audit — one artefact. The rApps are designed to run on a Virtual RIC: a software Non-RT RIC deployed standalone, not as part of an SMO, hosting twin-gated optimisation for a live 5G NR network.

Step 1 — Load a single tower or a cluster

Loading builds the twin of the chosen site(s) — Sionna RT ray tracing over the open San Francisco scene of the published study — and shows the as-built configuration. Then select a function in Step 2.

Slice — slice optimiser (PRB shares between slices)

A learned policy (PPO, from the validated RANOpt core) sets the share of physical resource blocks each slice receives, scored through Sionna SYS PHYAbstraction and emitted only if it beats the current profile under guardrails — guarded acceptance, the same discipline as the twin gate. Energy — carried in the family, not a separate built rApp

Stated plainly: there is no standalone energy rApp yet. Energy enters this family three ways today:

  • Policy lineage. The RANOpt study behind the slice policy validated a +7.21% energy improvement (mean over 5 seeds, all 5 seeds improved) from the same optimisation machinery.
  • Utilisation pressure. The slice reward carries a PRB-utilisation term (target 88%): allocations that waste lit capacity score worse, which is the pressure that makes carrier and cell sleep worthwhile.
  • The twin turns things down. The capacity search is not an up-only optimiser: in the cluster run on this page it cut Tower A's power by 2 dB because the twin showed the network was better for it.

The stated extension is a twin-gated sleep-window rApp: candidate sleep windows proven in the twin before any carrier is switched off. It is not built yet, and this page does not pretend otherwise.

Audit — MCS audit (is the base station's link adaptation telling the truth?)

The twin derives, for each receiver, the reference MCS its signal quality should produce. The audit compares that with the MCS distribution the base station actually used (from its PM histograms) and fits the single number that explains the difference: the effective OLLA offset. Corrections are bounded to ±4 dB, need an estimated offset above 1 dB, and are emitted only if the twin verifies a spectral-efficiency gain of at least 2%. Controlled verification test — a different, deliberate experiment. A hidden fault was planted: an effective OLLA offset of −3 dB under a configured 0 dB. The audit recovered it exactly — −3.00 dB in all three sectors — and the +3 dB correction restored spectral efficiency by +15.4% / +15.4% / +16.7% per sector. Negative control: against a healthy base station (true offset 0 dB) it estimated +0.00 dB and took no action.

The PM data in the prototype is a simulated stand-in; the histogram schema is the contract the audit is written against. Connecting it to a vendor's live counters is integration work, not research.
