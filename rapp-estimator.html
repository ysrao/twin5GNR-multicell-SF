rApp Estimator

Based on the twin-in-the-loop rApp description (v4, Virtual RIC). Step 1: the cluster comes in as a file — the site database export. Step 2: the network counters are ingested automatically from the SMO/OSS performance-management export — no operator types them in. Step 3: select the function and get an estimate of what the rApp would deliver, before any twin is built.

Step 1 — Cluster file (site database export)

Step 2 — Network counters (ingested, not typed)

In deployment the Virtual RIC collects the SMO/OSS bulk PM export automatically each PM cycle (O1 file collection or the operator's data feed) and parses the standard 3GPP counters itself. This page accepts that same export file. The values below were ingested from the study network's recorded counters (source: recorded PM export, study network) — load your own export to replace them, or edit a value only to run a what-if.

The audit's offsets are the output of its histogram fit on the PM export — the audit computes them itself from the MCS histograms in the same ingested file; they are shown here because the fit is the audit's first stage.

Step 3 — Select the function and estimate

Estimate only — the twin run is the proof. This page sizes the opportunity from the cluster file and the ingested counters, using the verified prototype results as calibration anchors (each estimate names its anchor). It does not replace the twin: the settings themselves, and the decision to apply them, come only from a twin run under the guardrails.

Calibration anchors: twin optimiser single-site run (coverage 81.3% → 88.8%, SE 2.82 → 2.93) and cluster run (39.5% → 40.9%, SE 2.08 → 2.26) on the published San Francisco study (Zenodo DOI 10.5281/zenodo.24210760); slice reward formula and targets from the accepted CCNC 2027 paper's validated model; energy anchor +7.21% from the RANOpt validation (5 seeds); audit gains from the recorded MCS audit run.
